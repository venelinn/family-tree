# Languages

English and Bulgarian, via [`next-intl`](https://next-intl.dev). The conventions
follow the bgmtl project — a `localization` config, a `getMessages` map, and a
date-fns locale table — minus the CMS half, since a locale here is only a UI
language.

## Where the pieces live

| File | Role |
| --- | --- |
| `lib/localization.ts` | The locale list, the default, and the language names |
| `messages/<code>.json` | One catalogue per language; `en.json` is the reference |
| `lib/getMessages.ts` | Code → catalogue, with a fallback to the default |
| `lib/locale.ts` | Reads the chosen language from the cookie |
| `lib/locale-actions.ts` | Writes it — a server action, because only actions set cookies |
| `lib/date-format.ts` | date-fns locale + pattern per language |
| `i18n/request.ts` | The glue `next-intl`'s plugin looks for |
| `global.d.ts` | Types `t()` keys against `en.json` |
| `app/settings/page.tsx` | Where the language is chosen |

## Cookie, not a URL prefix

There is no `/en` / `/bg` segment and no middleware. A locale segment buys
shareable per-language links, and costs an `app/[locale]/` restructure plus a
rewrite of every `revalidatePath` call. For a two-page app read by one family
that trade wasn't worth it, so the choice lives in a `NEXT_LOCALE` cookie and
`/` stays `/`.

The consequence: setting the language has to invalidate everything, because
every rendered string on every route just changed. `setUserLocale` calls
`revalidatePath("/", "layout")` for exactly that reason — without it, navigating
back to the chart serves the client router cache's copy in the old language.

## Keys, not strings, below the components

`lib/facts.ts`, `lib/layout/add-slots.ts` and `lib/tree-ops.ts` all used to
return English. They now return **keys**, and the component or the server action
translates:

- a fact's `titleKey` is `"birthOfDaughter"`, not `"Birth of daughter"`
- an add-slot's `slot` is `"sister"`, not `"Add sister"`
- a failed write raises `TreeOpError("alreadyHasFather", { name })`, and
  `lib/actions.ts` turns that into a sentence at the request boundary

This isn't ceremony. Those modules run on both sides of the server/client
boundary and none of them has any business knowing which language the reader
picked. `ErrorCode` and `SlotKey` are unions checked against `en.json` by the
type augmentation, so a key that loses its message fails to compile.

## Grammar the catalogue has to carry

Two things that an English-shaped implementation gets wrong and that ICU handles
in the message rather than in code:

**Plurals.** The reveal bars say `+ 2 родители`. A `count === 1 ? "parent" :
"parents"` in the component encodes English plural rules into every language, so
the count goes to the catalogue instead:
`"{count, plural, one {# родител} other {# родители}}"`.

**Gender agreement.** Bulgarian inflects for the subject: a man is *Роден*, a
woman *Родена*; *Починал* / *Починала*; *партньор* / *партньорка*. The person's
sex is passed to the message and the catalogue decides whether it matters —
English ignores it via `{sex, select, other {Born}}`. That's why "Add partner"
is two keys, `partnerMale` and `partnerFemale`, rather than one.

## Dates

Dates in the tree are free text on purpose — a source says "about 1910" as often
as it gives a full date, and the GEDCOM parser only produces an ISO string when
it had a complete day/month/year. `formatTreeDate` formats the ISO ones and
passes everything else through untouched; rewriting "about 1910" would invent
precision the record doesn't have.

Pattern and locale are per language (`MMM d, yyyy` for English, `d MMM yyyy` for
Bulgarian). `parseISO` on a date-only string gives local midnight, so the
calendar day survives formatting whatever the server's zone is — which is why
`date-fns-tz` isn't used here. Nothing in this tree carries a time.

## Adding a language

Three steps, and **each one fails by falling back rather than erroring**, so a
missed step looks like "translations aren't working":

1. `lib/localization.ts` — add the code to `locales` and a name to `localeNames`
2. `messages/<code>.json` — copy `en.json` and translate it
3. `lib/getMessages.ts` and `lib/date-format.ts` — import the catalogue and the
   date-fns locale, and give it a date pattern

Then `pnpm i18n:check`, which compares every catalogue against `en.json` both
ways. A missing key renders as the key itself at runtime, which is easy to miss
in a language you don't read; a leftover key after a rename is worth knowing
about too.

The font already covers it if the language is Latin or Cyrillic — `app/layout.tsx`
loads both Geist subsets. Anything else needs its subset adding there.
